## 1. 意图与缘由

DeepSeek Harness（下称 DSH）桌面端原本只能通过「添加插件」对话框手填包名、Git 地址或本地路径来装插件，用户得先去别处（awesome 列表、GitHub topic、各种网页目录）找到插件再回来粘贴。

DSH 0.2.1-alpha.4（2026-10-15）起，官方加了一个实验性组合包「自定义插件市场」（`@deepseek-ai/dsh-experimental-plugin-market-bundle`），在插件页提供「发现」标签页：添加一个索引源 URL 后，可浏览、搜索、按分类筛选、看详情、一键安装。官方**只做界面不做市场**，没有任何默认索引源。

用户已在桌面端 0.2.1-rc.2 上实测「发现」页：功能可用，但**界面不够吸引人**，具体是「没有对插件进行详细的分类和展示」——一行一条的列表、标题直接显示包名、详情页只有一行简介 + 来源表 + 版本列表。

用户最初的痛点来自社区插件市场「DSH Plugin Hub」（疑为 `dshplugin/dsh-plugin-hub`，v2.0.3）：**装完之后看不出在哪里用**——它藏在「设置」弹窗里，装好后界面没有任何变化提示入口，用起来也局促。同类的 `dsh-market/dsh-market`（7k+ 星）也在桌面端积累了大量问题：装完看不到入口（#139）、装完桌面端起不来（#869、#741）、自管安装 / 卸载 / 自更新与桌面端插件管理器冲突（#903、#900、#922 等）。

本项目要做的是：**一个装完就能找到、界面更吸引人、展示更详细的插件商城，以及一份由用户亲自收录、审核过的插件目录。** 用户之后会持续收录插件；目录质量（中文名、要点、截图、审核结论）是商城的核心价值，界面是它的载体。

## 2. 目标

0. **装完就知道在哪用**（最高优先级）【用户定】：
   - 刚装完：用户是在「插件」页安装的，安装完成后这个页面**不用重启**就出现「商城」标签页，并且**第一次自动切到商城**，弹出一句「商城已就绪」。
   - 以后每次用：左侧边栏常驻一个「商城」图标入口（`sidebar.panellist` 插槽），点击直接打开商城。
   - 兜底：商城插件在「已安装」中的详情页提供「打开商城」按钮（`plugins.detail.actions` 插槽）。
1. 在 DSH 桌面端（同样适用于 Web 端）的插件页增加一个「商城」标签页，与「已安装」「发现」并列。【用户定：方向 A 应用商店式】
2. 商城首页是**应用商店式**布局：【用户定】
   - 顶部「本周精选」大横幅，主推一个插件；
   - 下方若干**主题分区**（如「让界面更顺手」「智能体增强」），每个分区横排一组大图标卡片，带「全部 ›」进入该分区完整列表；
   - 底部「按分类浏览」入口。
3. 插件**详情页**包含以下 8 个模块：【用户定：清单第 1–8 项】
   1. 大图标 + 中文名 + 一句话卖点（替代直接显示包名）
   2. 数据条：GitHub 星标、npm 周下载、最近更新
   3. 截图 / 动图
   4. 「能做什么」要点（3–5 条）
   5. 需要的权限（是否联网、读写文件、给 Agent 注册工具等）
   6. 审核结论 + 兼容徽章（「已审核」「兼容当前 DSH 版本」）
   7. 详细介绍（README）+ 更新日志（以及全部版本、来源信息）
   8. 同类插件 / 同作者其他插件推荐
4. 安装走 DSH 官方安装流程，用户点「安装」后看到的是 DSH 自带的安装检查对话框。
5. 一份由用户收录、维护的插件目录，按官方索引格式 1 发布，**同时能被官方「发现」页直接读取**（没装商城插件的人也能用）。【我的判断】
6. 收录流程半自动：脚本抓取能自动拿到的数据、起草需要人写的字段，用户核对修改并标记审核通过后发布。【我的判断，用户未反对】

## 3. 非目标

- **用户评分与评价**。【用户定：未选第 9 项】因此**整个项目不需要后台服务**，所有数据来自静态文件。
- 替代「已安装」标签页的管理功能（启用 / 停用 / 配置 / 卸载仍由 DSH 自带页面负责）。
- 自建安装流程或绕过 DSH 的安装检查、构建脚本审批、兼容性拒绝。
- 升级操作（官方「发现」页也只显示「有新版本」状态，不做升级；商城同样只显示状态，点击跳到「已安装」里该插件的页面）。
- 收录所有能找到的插件。第一版只收两类：**界面优化类**和**功能性**插件，数量不设目标，宁缺毋滥。【用户定】
- 支持 DSH 0.2.1-rc.2 之前的版本。
- 发布到 npm。【用户定】

## 4. 反目标（技术上能跑，但出现即算失败）

- 装完后用户找不到商城在哪（重蹈 DSH Plugin Hub 的覆辙），或者必须重启才出现入口。
- 装上商城后桌面端起不来，或者商城拖垮其他界面（重蹈 dsh-market #869 的覆辙）。商城的浏览器端出错时只能影响它自己的标签页。
- 自己执行安装、卸载、更新、重启，或者改写 profile / `cordis.patch.yml`（重蹈 dsh-market #903、#900 的覆辙）。
- 把没审核过的插件标成「已审核」，或审核结论对应的版本和实际安装的版本不一致却不提示。
- 「需要的权限」把启发式扫描的结果说成确定结论。界面上必须注明这是审核时扫描源码得出的。
- 数据缺失时页面显得破损（空白横幅、裂图、`undefined`）。每个字段都要有体面的缺省展示：没截图就不显示截图区，没有中文名就用英文名或包名。
- 商城读不到索引时整页报错不可用。应显示简短说明和「重试」，并保留上次成功的内容。
- 索引改动导致官方「发现」页读不了这份索引（扩展字段破坏了格式 1 校验）。
- 写进 TakoRAG 工作区（`D:\MCP\llmwiki-master`）或任何与本项目无关的仓库。

## 5. 约束与已核实的事实

以下事实来自 DSH 源码 `deepseek-ai/deepseek-harness` master `687f282e`（2026-10-17，版本 0.2.1-rc.2）：

| 事实 | 出处 |
|---|---|
| 插件页对第三方开放 `plugins.tab` 插槽（kind: list, scope: root），官方「发现」就是通过它挂进来的 | `packages/client/ui-plugin-manager/src/client/slot-contract.ts` |
| 标签页拿到的 owner props：`install({ spec, registry?, title, version })` 打开插件页自己的安装对话框，直接进入检查界面、不显示 spec 表单；`openPackage(name)` 切到「已安装」并打开该包页面 | 同上 `PluginTabProps` |
| 官方「发现」的注册写法：`ctx.slots.register({ name: 'plugins.tab', id, label, locale, inject })`，`inject = ['slots','locale','remote', ...]` | `packages/client/ui-plugin-market/src/client/index.ts` |
| 第三方插件分发形式：npm 包，`package.json` 声明 `dsh.bundle.patch` 指向 `cordis.patch.yml`，patch 用 `insert` 插入插件行；`engines.dsh` 声明支持的 DSH 版本范围，不满足时安装被拒 | `docs/user/develop/basic/publish.zh.md`；官方市场 bundle 的 `package.json` 与 `cordis.patch.yml` |
| 官方市场组合包是 Host 服务（`@deepseek-ai/dsh-plugin-market`）+ Web 标签页（`@deepseek-ai/dsh-client-ui-plugin-market`）两行；索引由 Host 读取（理由：CORS、走进程代理、在不可信数据入口处校验） | `.agents/notes/implemented/feature/2026-10-02-plugin-market-discover.zh.md` |
| 索引格式 1：根 `format/title/description/metadata{categories,labels,sortKeys}/plugins`；插件 `name/title/description/icon/author/homepage/repository/metadata{category,labels,keywords,sortKeys}/dist-tags/versions`；版本 `version/publishTimestamp/source/engines.dsh`。`LocalizedText` **要求有英文**。图标 data URL ≤ 32 KiB 或相对 / https URL | `.agents/notes/implemented/feature/2026-10-02-plugin-market-index-format.zh.md` |
| **读取器和校验器在每一层都忽略未定义的成员**，因此格式 1 可以加可选扩展字段而不破坏官方读取 | 同上（第 178、224 行） |
| 官方参考生成器 `apps/plugin-market-generator`：从 npm 包名 / Git URL 列表生成合法 `index.json`（含图标、多语言标题、版本、`engines.dsh`），只下载不执行代码 | `apps/plugin-market-generator/README.zh.md` |

其他约束：

- DSH 处于开发者预览，迭代快、可能破坏性变更。商城插件必须声明 `engines.dsh`（起点 `>=0.2.1-rc.2`），并在 README 写明已验证的 DSH 版本。
- 中国大陆用户访问 GitHub raw 不稳定。索引和资源的公开地址需在国内可达（见 §6.4）。
- 外观跟随 DSH 主题（含深色模式），桌面端窗口宽度下布局不溢出。
- 界面语言以中文为主，英文兜底（格式 1 的 `LocalizedText` 必须带英文）。

## 6. 已定的做法

### 6.1 交付物

一个公开仓库，包含三部分：

| 部分 | 内容 |
|---|---|
| 商城插件 | 一个 DSH 组合包，装进 DSH 后在插件页增加「商城」标签页。**不发布到 npm，通过 GitHub 分发**（见 §6.1.1） |
| 插件目录 | 用户维护的收录清单 + 生成出的索引文件与静态资源（图标、截图、详情数据） |
| 收录工具 | 维护者在本机运行的脚本：抓取、起草、扫描、校验、生成 |

#### 6.1.1 分发：GitHub，不用 npm【用户定】

- 商城插件和插件目录**都只放在 GitHub** 上，不发布到 npm。
- 用户安装商城插件的方式：在 DSH「添加插件」里填 GitHub 地址（如 `github:yang051211/dsh-plugin-store#<tag>`，具体写法以技术验证结果为准）。
- 已知的坑（`docs/user/develop/basic/publish.zh.md`「从 GitHub 安装：构建脚本这道坎」）：Git 安装拿到的是源码，不会运行 `build`。如果靠 `prepare` 脚本在安装时构建，pnpm ≥10 要求用户手动把包加进 `allowBuilds` 授权，体验差，而且等于允许安装时执行代码。
- **采用的做法**【我的判断】：**把构建产物提交进仓库**（或放在专门的发布分支 / tag 上），不设置 `prepare` 脚本。这样 Git 安装拿到的已经是可以直接加载的代码，用户无需批准构建。官方文档没有直接写这种做法，必须在技术验证中实测（见 §6.4 的第 ④ 项）。
- 安装说明建议用户锁定 tag 或 commit，避免后续推送悄悄改变已安装的代码。
- 商城插件本身也作为一个条目收录进索引（`source.type: git`），这样只用官方「发现」页的用户也能从那里装上商城。【我的判断】
- 仓库根目录或子目录能否直接作为 Git 安装目标（pnpm 支持 `#path:` 子目录写法），以及仓库目录结构，留给实现者，但必须满足「填一个 GitHub 地址就能装」。

#### 6.1.2 包结构：参照社区插件的通行做法

调研了 dsh-market、AwesomeHou/dsh-plugin-marketplace、Han-1413141/dsh-ui-hub、PerryLink/dsh-session-pin、adrianleb/dsh-tmux-cc、Winnie-0721/dsh-plugin-market 后发现，通行做法是**一个包、一行 patch，同时带 Host 与浏览器两半**：

- `exports["."]` → `lib/index.js`（Host 端），`exports["./client"]` → `lib/client.js`（浏览器端）；
- `package.json` 声明 `dsh.bundle.patch` 和 `dsh.client: { platform: "web", inject: [...] }`，DSH 会据此自动把 `./client` 注入页面；
- `cordis.patch.yml` 只 `insert` 一行，`name` 为包名；
- `lib/` 构建产物提交进仓库（上述多数仓库都这样做），`locale/zh.json`、`locale/en.json` 存放文案。

所以 §6.4 中的「Host + 客户端」不需要两行 patch，按这个结构用一行即可。【我的判断】

### 6.2 技术栈【我的判断】

TypeScript + React，沿用 DSH 官方客户端插件的写法（以 `ui-plugin-market` 为参照），通过 `plugins.tab` 插槽注册标签页，通过 owner 的 `install` / `openPackage` 安装和跳转。

### 6.3 数据模型：格式 1 + 扩展字段【我的判断】

- **列表索引** `market/index.json`：严格符合官方格式 1，官方「发现」页可直接读取。商城需要的额外信息放在**带命名空间的扩展成员**里（如根上的 `store`、插件上的 `store`，具体键名留给实现者），官方读取器会忽略它们。
  - 根扩展：本周精选（指向某插件 + 横幅文案 / 配色或横幅图）、主题分区（标题、排序、包含的插件）、分类的中文标题与排序。
  - 插件扩展：一句话卖点、星标 / 周下载 / 最近更新、审核状态与审核的版本、兼容徽章所需信息、是否有详情数据。
- **详情数据** `market/plugins/<安全化包名>.json`：截图列表、「能做什么」要点、权限扫描结果、审核说明、README（Markdown）、更新日志、同类与同作者推荐。打开详情页时才读取，让列表索引保持小巧。【我的判断】
- 分类使用格式 1 的 `metadata.categories`（每个插件一个分类），中文标题放在 `LocalizedText.zh`。主题分区是商城自己的概念，不占用官方分类。
- 发布前，每份索引必须通过官方校验器 `@deepseek-ai/dsh-plugin-market-index` 的校验。

### 6.4 数据如何到达用户【我的判断】

- 索引和资源随仓库发布，通过 **jsDelivr**（`cdn.jsdelivr.net/gh/<用户>/dsh-plugin-store@<tag或分支>/market/...`）以 https 提供，兼顾国内访问。是否另配 GitHub Pages 作为备用地址，留给实现者。
- 商城插件内置默认索引地址，同时允许用户在设置里改成其他地址（便于自建或镜像）。
- **推荐由 Host 侧读取索引**（与官方一致：走 DSH 进程代理、避开 CORS、在入口处校验与限大小）。也就是说，商城插件很可能需要「Host 服务 + Web 标签页」两行。若实现者核实浏览器端直接读取在桌面端与 Web 端都可靠，也可以只做客户端一行，但需在计划里说明理由。【留给实现者，带推荐】
- 安装状态（未安装 / 已安装 / 有新版本 / 随 DSH 提供）与兼容性判断的获取方式留给实现者。官方做法是 Host 侧通过 `pluginManager` 只读调用 + `evaluatePluginCompatibility`，可作参照。
- **计划的第一步必须是技术验证**【我的判断】：做一个最小的第三方组合包，在 monorepo 之外独立构建（官方客户端打包预设和 Host 端的 typert 代码生成都在 monorepo 内），装进 DSH 0.2.1-rc.2 桌面端，验证六件事：① `plugins.tab` 标签页能显示；② 能读取到外部索引；③ `install` 能打开官方安装对话框；④ 通过 GitHub 地址安装这个最小包（构建产物已提交进仓库、没有 `prepare`）时，不需要批准构建也能装上并正常加载；⑤ 安装完成后**不重启**标签页就出现，并且能自动切过去；⑥ `sidebar.panellist` 侧边栏入口能显示，点击后能打开插件页的商城标签页。另外，故意让商城浏览器端抛异常，确认桌面端仍能启动、其他界面不受影响。验证结果决定采用「Host + 客户端」还是「纯客户端」。
- **不依赖官方实验组合包「自定义插件市场」**【我的判断】：商城必须能独立工作，不要求用户另外开启它。即使开启了，它的 `pluginMarket` 服务也会剥掉扩展字段，借用它的意义不大。

### 6.5 安装

卡片和详情页上的「安装」先弹出商城自己的确认（显示插件名、版本、来源、审核状态和一句信任提示），确认后调用 owner 的 `install({ spec, registry?, title, version })`，后续全部由 DSH 安装对话框接管。已安装的条目显示「已安装 / 有新版本」，点击调用 `openPackage`。【我的判断，参照官方做法】

### 6.6 页面

- **首页**：精选横幅 → 主题分区（横向卡片组，「全部 ›」）→ 分类入口。【用户定】
- **列表页**（「全部 ›」或点分类后进入）：卡片网格 + 搜索 + 排序。搜索框放在首页顶部还是列表页，留给实现者，但首页必须有进入搜索的入口。【我的判断：有搜索】
- **详情页**：§2 第 3 条的 8 个模块，布局参照讨论中的草图：头部（图标、中文名、卖点、徽章、安装按钮、数据条）→ 截图横排 →「能做什么 / 需要的权限 / 审核结论」三栏 → 标签页（详细介绍、更新日志、全部版本、来源信息）→ 同类 / 同作者推荐。
- 返回时保持之前的滚动位置、搜索与筛选状态。

### 6.7 收录流程【我的判断】

1. 用户在收录清单（仓库内一份 YAML/JSON，格式留给实现者）里加一行：npm 包名或 Git 地址 + 分类 + 所属主题分区。
2. 脚本抓取：npm 元数据、`engines.dsh` / peer 范围、图标、README、更新日志、GitHub 星标、npm 周下载、最近发布时间。生成格式 1 部分时遵循官方 `plugin-market-generator` 的规则（见下文「不依赖官方生成器包」）。
3. 脚本起草：中文名、一句话卖点、「能做什么」要点（从 README 提炼）；从 README 中提取截图候选。
4. 脚本扫描源码（只下载和读取，绝不执行），得出权限候选：是否联网、是否读写文件、是否注册 Agent 工具、是否有 install/postinstall 脚本、依赖数量等。
5. 用户核对并修改起草内容，填写审核结论、绑定审核的版本，标记「审核通过」。**只有审核通过的条目进入发布的索引。**
6. 脚本生成 `index.json` 与详情文件，跑官方校验，提交并打 tag 发布。

**审核绑定到版本，索引只列审核过的版本**【我的判断】：

- 发布的 `index.json` 中，每个插件的 `versions` 只包含审核通过的版本，`dist-tags.latest` 固定为最近一次审核通过的版本。官方「发现」页的读取器会丢弃扩展字段，看不到审核信息，所以只有这样做，官方「发现」页的用户才不会装到未审核的版本，§4 第一条反目标在两条路径上都成立。
- 上游发布新版本、尚未重新审核时：索引中不出现这个新版本。商城只在详情页用扩展字段提示「上游有新版本 x.y.z，待审核」，不提供安装。
- 「有新版本」状态以索引中审核过的最高版本为基准，不以上游最新版本为基准。

人写字段一律以收录清单里的人工值为准，重跑脚本不得覆盖人工修改。

**统计数据刷新**【我的判断】：第一版中，星标、周下载、最近更新只在维护者本机重跑脚本并发布时更新，界面上显示数据的截取日期。之后如果要做定时自动刷新（例如 CI 定时任务），只允许更新统计字段，不得改动审核内容或版本列表。这一项不在第一版范围内。

**不依赖官方生成器包**【我的判断】：官方 `plugin-market-generator` 是 monorepo 内的 `private` 包，没有发布到 npm，因此只能参照它的规则自行实现，或把需要的逻辑移植过来（MIT 许可，保留出处）。校验器 `@deepseek-ai/dsh-plugin-market-index@0.2.1-rc.2` 已发布到 npm（2026-10-19 用 `npm view` 核实），直接作为开发依赖使用。

### 6.8 首批内容【用户定】

只收**界面优化类**和**功能性**插件。候选来源可以是 awesome 列表、GitHub `dsh-plugin` topic、已有的社区索引，但每个插件都要单独过审。

**第一版交付时，目录里要有 2 个真实收录、审核通过的插件**【用户定】。建议界面优化类、功能性各选一个【我的判断】，具体选哪两个在实施过程中由用户确认。本周精选和主题分区都用这 2 个真实插件填充，不放虚构的示例条目。第一版的验收就基于这 2 个真实条目，在桌面端走通「首页 → 详情 → 安装」全流程。

## 9. 技术验证结论（2026-10-19，取代上文相应的待定项）

用户在桌面端 0.2.1-rc.2 上实测了 tag `spike-1`，详见 [docs/spike/2026-10-19-findings.md](../../spike/2026-10-19-findings.md)。由此定下：

- **分发**：`github:yang051211/dsh-plugin-store#<tag>` 可以直接安装，不需要批准构建（构建产物提交进仓库、不设 `prepare`）。安装说明必须写完整的 `github:` 地址，并提醒「安装源」保持 npm 官方源或中国大陆镜像源，**不要**设成自定义地址。设成自定义地址会把整个 profile 的依赖都改到那个源去解析，导致安装失败。
- **结构**：一个包、一行 patch，Host 端通过 `ctx.webServer.register` 提供路由，浏览器端通过 `dsh.client` 注入（取代 §6.4 中「Host + 客户端两行」的推荐）。
- **入口（目标 0）**：
  - 侧边栏「商城」入口 + **整页面板**（`sidebar.panellist` + `main` 插槽）是商城的主界面，用来「逛」；装完首次自动打开整页面板。
  - 插件页的「商城」标签页（`plugins.tab`）是**唯一能调用官方安装对话框的位置**。整页面板拿不到 `install`，插件页切换标签的方法也没有对外开放。
  - 因此需要设计一个「从整页面板交接到插件页标签页完成安装」的方式，例如：整页面板点「安装」后，记下要装的插件、跳到插件页，并提示用户切到「商城」标签页，标签页打开后自动弹出安装确认。具体做法在计划 3 中设计并实测。
  - 目标 0 中「插件页标签页首次自动切换」改为「首次自动打开整页面板」，已实测可行。
- **错误边界（反目标补充）**：DSH 会把插件的渲染错误限制在插件自己的区域里，但该区域会变成**白屏**，没有任何提示。商城的每个界面（整页面板、标签页）都必须自带错误边界：出错时显示简短说明和「重试」，并且有测试覆盖。
- **安装状态**：官方安装对话框遇到已装的插件会报「该插件已安装」。商城卡片和详情页应提前显示「已安装」，不要等用户点了才被告知（对应 §6.5）。
